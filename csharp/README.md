# OpenTuya Sync на C#

Полная переработка проекта на C# (.NET 10, WPF). Интерфейс намеренно
классический — системные цвета и шрифты Windows, без оформления
Python-версии.

Python-версия осталась в корне репозитория и не тронута: можно сравнить
поведение и вернуться к ней в любой момент.

## Что важно знать перед началом

**Служба Windows не может захватывать экран.** Службы работают в
изолированной сессии 0 и не видят рабочий стол пользователя — это
ограничение операционной системы, а не выбор реализации. Поэтому
приложение разделено на две части:

| Часть | Где работает | Чем занимается |
|---|---|---|
| **OpenTuyaSync.Service** | Служба Windows | Подключения к лампам, протоколы (Tuya, WLED, Hue, Bluetooth), рассылка цвета |
| **OpenTuyaSync** (агент) | Сессия пользователя | Интерфейс, захват экрана, звук, горячие клавиши |

Такое разделение даёт то, ради чего служба и нужна: устройства остаются
подключёнными и цвет доходит до лампы, даже когда окно приложения закрыто.
Захват при этом делает агент, потому что иначе его сделать нельзя.

```
  OpenTuyaSync.Service/     служба Windows + установщик

  tools/                    утилиты диагностики (см. ниже)
```

## Сборка

Требуется .NET SDK 10.

```bash
cd csharp
dotnet build OpenTuyaSync.slnx -c Release
publish.bat          # кладёт готовые файлы в csharp\dist (для отладки)
publish-release.cmd  # собирает релиз в csharp\Releases
build-tools.bat      # собирает утилиты диагностики
```

`publish.bat` создаёт `csharp\dist` — **27,7 МБ и 59 файлов** (для
сравнения: сборка Python-версии — 287 МБ). Используется
`--self-contained false`: установленный .NET не требует 150 МБ рантайма
на каждое приложение, а скорость та же.

## Релиз

```bash
publish-release.cmd            # с паузой в конце
publish-release.cmd --quiet    # без паузы, для автоматической сборки
```

Скрипт каждый раз собирает папку заново, поэтому старые файлы в релиз не
попадают. Что получается:

```
Releases\
  OpenTuyaSync.exe          приложение: интерфейс и захват экрана
  OpenTuyaSync.Service.exe  служба: управление устройствами
  НАСТРОИТЬ.bat             установка службы и первый запуск
  ПЕРЕЗАПУСК.bat            перезапуск приложения
  ЧИТАТЬ.txt                краткая инструкция для пользователя
  config.json               настройки по умолчанию
  icon.ico                  значок
  *.dll, runtimes\          все нужные библиотеки
  tools\ColorTest\          проверка подсветки на весь экран

Итого около 29 МБ.
```

В релиз не попадают отладочные символы (`*.pdb`) и файлы, которые
накопились при отладке (`agent_alive.txt`, `service_link.log`, кадры
самопроверки теста). Текст самого скрипта — только ASCII: `cmd` читает
командный файл в текущей кодовой странице, и кириллица в нём ломала бы
разбор команд. Кириллические имена файлов скрипт берёт из папки
`release-files`, не задавая их текстом.

## Интерфейс

Три вкладки.

**Автоматически** — выбор источника (Ambilight, музыка, вспышки), выбор
монитора или устройства вывода звука, пределы яркости, запуск и
остановка, журнал событий.

**Вручную** — ползунки RGB, системный диалог выбора цвета, предпросмотр,
включение и выключение ламп.

Любое действие здесь **само останавливает автоматическую подсветку**: иначе
движок перебивал бы выбранный цвет несколько раз в секунду. Раньше вместо
этого показывалось окно с требованием остановить подсветку вручную, и
складывалось впечатление, что программа зависла.

**Настройки** — всё, что касается конфигурации:
- **устройства**: список, добавление, изменение, удаление, проверка связи;
- **поиск и выбор устройства**: сканирование локальной сети (Tuya) и
  поиск по Bluetooth, найденное подставляется в поля автоматически;
- **параметры устройства**: название, тип, Device ID, IP, Local Key,
  версия протокола, персональная яркость, включение;
- **горячие клавиши**: назначение сочетаний для запуска, смены источника
  и яркости;
- **система**: автозапуск при входе, старт свёрнутым в трей, автостарт
  подсветки, возврат ламп в прежнее состояние, установка и удаление
  службы.

Окно закрывается в трей, а не завершает работу: иначе подсветка гасла бы
при случайном нажатии крестика.

## Горячие клавиши

По умолчанию не назначены. Нажмите «Назначить» и затем сочетание клавиш;
`Esc` отменяет. Регистрация глобальная — сочетания работают, когда окно
свёрнуто. Если сочетание занято другой программой, приложение сообщит об
этом: это не ошибка настройки, а нормальное поведение Windows.

Доступные действия: запуск и остановка подсветки, следующий источник,
яркость больше, яркость меньше.

## Автозапуск

Флажок в настройках прописывает приложение в
`HKEY_CURRENT_USER\...\Run` с ключом `--minimized`. Права администратора
не нужны, действие распространяется только на текущего пользователя.

## Установка службы

Из интерфейса: вкладка «Настройки» → блок «Служба Windows». Приложение
запросит права администратора (UAC) и запустит установку.

Из командной строки от администратора:

```bash
OpenTuyaSync.Service.exe install
OpenTuyaSync.Service.exe uninstall
OpenTuyaSync.Service.exe status
```

Служба ставится с типом запуска «отложенный автоматически» и
настраивается на перезапуск при падении.

### Предустановленные параметры

Устройства можно задать прямо при установке службы — тогда они
применяются при каждом её старте, а менять конфигурацию через интерфейс
запрещается (служба отвечает «запущена с предустановленными
параметрами»).

```bash
OpenTuyaSync.Service.exe install ^
  --preset "Кухня|tuya|DEVICEID|192.168.1.50|LOCALKEY|3.5" ^
  --preset "Лента|wled|192.168.1.60" ^
  --preset "Мост|hue|192.168.1.70|КЛЮЧ|1" ^
  --preset "Панель|elk|BE:32:XX:XX:XX:XX"
```

Формат записи: `имя|тип|поле1|поле2|...`

| Тип | Поля |
|---|---|
| `tuya` | Device ID, IP, Local Key, версия протокола (необязательно) |
| `wled` | IP |
| `hue` | IP моста, ключ пользователя, ID лампы |
| `elk` | MAC-адрес |

## Производительность

Замеры на этой машине (8 ядер):

| Показатель | Значение |
|---|---|
| Передача кадра цвета агентом в службу | **0,14–0,26 мс** |
| Размер публикации | **27,7 МБ** |
| Память агента | ~85 МБ |
| Захват экрана (Ambilight, GDI) | **0,39% одного ядра** |
| Публикация Python-версии (для сравнения) | 287 МБ |

Что сделано для экономии ресурсов:

- **Размер выборки кадра — 64×36 пикселей.** Одна лампа не покажет
  детали, а усреднение по тысячам пикселей каждый кадр — чистая трата
  процессорного времени. Кадр 64×36 обрабатывается за десятки
  микросекунд.
- **Отправка только при заметном изменении цвета.** Статичная картинка не
  гоняет трафик и не изнашивает светодиоды.
- **Сетевой обмен вынесен в отдельные потоки** с пониженным приоритетом:
  подвисание сети не проседает кадры.
- **Потоки захвата — с повышенным приоритетом:** плавность подсветки
  важнее фоновых задач.
- **Ограничение частоты отправки** на каждом устройстве (Tuya — 90 мс,
  Hue и WLED — 90–100 мс, Bluetooth — 150 мс): больше лампа не переварит.
- **Обмен с службой через локальный сокет** на петлевом интерфейсе: снаружи
  порт недоступен, брандмауэр не затрагивается; соединение открывается на
  каждую операцию и стоит доли миллисекунды.
- **Устройства D3D11 переиспользуются**, staging-текстура создаётся один
  раз, а не на каждый кадр.

## Работа с полноэкранными играми

Основной путь захвата — **DXGI Desktop Duplication**. Он видит игры в
полноэкранном режиме, потому что Windows отдаёт их как независимый
флип-вывод, и не читает видеопамять процессором так, как это делает GDI.

Если DXGI недоступен (удалённый рабочий стол, ограниченная сессия,
старый драйвер), приложение автоматически переходит на **GDI** и
продолжает работать, только без эксклюзивного полного экрана. Активный
бэкенд видно в строке состояния и в журнале.

Проверить, что доступно в вашей системе:

```
tools\DxgiProbe\bin\Release\net10.0-windows\OpenTuyaSync.DxgiProbe.exe
```

### Почему здесь используется SharpDX

Первая версия захвата обращалась к DXGI напрямую, через самодельные
объявления COM-интерфейсов. Это не заработало: `DuplicateOutput` проходил
успешно, а первый же `AcquireNextFrame` всегда возвращал
`DXGI_ERROR_UNSUPPORTED`. Независимая проверка через SharpDX на той же
машине отдала кадры сразу — то есть дело было в ручных объявлениях, где
неизбежно расходятся порядок методов и сигнатуры, а COM такие ошибки не
прощает. В итоге interop переписан на SharpDX, который проверен временем.

## Подпись и предупреждение SmartScreen

Windows показывает окно «Система Windows защитила ваш компьютер» при
запуске неподписанного приложения. Это не признак заражения: Defender
реагирует на отсутствие репутации, а не на содержимое. Собранный локально
файл её не имеет по определению.

**Вариант 1: просто нажать «Выполнить в любом случае».** Ничего страшного
не произойдёт.

**Вариант 2: подписать самоподписанным сертификатом** — убирает
предупреждение на своей машине:

```powershell
powershell -ExecutionPolicy Bypass -File sign-selfsigned.ps1
```

Скрипт создаёт сертификат, добавляет его в доверенные корневые текущей
учётной записи (права администратора не нужны, изменение затрагивает
только вас) и подписывает оба `.exe`. Windows покажет окно
«Предупреждение системы безопасности» — нужно нажать «Да».

Откат:

```powershell
powershell -ExecutionPolicy Bypass -File sign-selfsigned.ps1 -Rollback
```

**Ограничение, о котором важно знать:** для других людей это не
сработает. Чтобы предупреждение не появлялось на чужом компьютере,
сертификат должен быть выдан удостоверяющим центром (платный). В репозитории
такого нет и быть не может.

## Ошибки, которые уже были найдены и исправлены

Полезно знать, потому что они типичны для WPF.

**Падение при запуске из-за событий, срабатывающих при разборе XAML.**
В разметке у радиокнопки стоит `IsChecked="True"`, а у ползунков —
начальные значения. События `Checked` и `ValueChanged` вызываются **до**
того, как созданы остальные элементы окна, поэтому обработчики падали с
`NullReferenceException`, и окно не открывалось вовсе. Все такие
обработчики проверяют поля на `null`.

**Падение при показе окна из-за инвариантного режима глобализации.**
`InvariantGlobalization` экономит немного памяти, но WPF разрешает
культуру для привязок и без неё падает с «Cannot find non-neutral culture
related to 'en-us'». В проекте агента этот режим отключён.

**Падение службы при остановке.** Рабочий цикл службы останавливал сервер
канала, а затем контейнер зависимостей освобождал его повторно. Второй
вызов падал на уже освобождённом `CancellationTokenSource`, и служба
завершалась с необработанным исключением — в журнале Windows это выглядело
как падение службы. Теперь остановка и освобождение разделены, а `Dispose`
безопасен при повторном вызове.

**Интерфейс не замечал перезапуск службы.** Клиент канала проверял только
`IsConnected`, а у канала это свойство ещё какое-то время возвращает `true`
после того, как служба уже завершилась. Первая же отправка в мёртвый канал
падала, и приложение продолжало показывать «Служба не отвечает», хотя
служба уже работала. Теперь отправка при обрыве повторяется один раз с
переподключением. Проверка:

```
tools\ReconnectTest\bin\Release\net10.0-windows10.0.19041.0\OpenTuyaSync.ReconnectTest.exe
```

Обе ошибки ловит проверка интерфейса:

```
tools\UiTest\bin\Release\net10.0-windows10.0.19041.0\OpenTuyaSync.UiTest.exe
```

Она строит главное окно, раскладывает его и убеждается, что вкладки на
месте. Запускайте её после правок разметки.

## Важно: повторная публикация снимает подпись

Команда `publish.bat` перезаписывает файлы в `dist`, и подпись теряется.
После каждой публикации подписывайте заново:

```powershell
powershell -ExecutionPolicy Bypass -File sign-selfsigned.ps1
```

Перед подписью нужно остановить приложение и службу — иначе файлы заняты:

```powershell
Get-Process -Name OpenTuyaSync* | Stop-Process -Force
sc.exe stop OpenTuyaSync
# ... подпись ...
sc.exe start OpenTuyaSync
```

### Bluetooth-устройства обслуживает приложение, а не служба

Это важное архитектурное решение, и вот почему оно такое.

Служба Windows работает в **изолированной сессии 0**, и устройства
Bluetooth Low Energy ей недоступны: операции GATT требуют сессии
пользователя. Проверено на практике — лента находится поиском из
приложения (сессия 1) и не находится из службы (сессия 0), причём Windows
сообщает именно «устройство не найдено», а не «нет прав».

Поэтому Bluetooth-ленты обслуживает приложение: цвет уходит в ленту
напрямую, минуя службу. Для пользователя разницы нет — лента получает тот
же цвет в тот же момент. Состояние Bluetooth показано отдельно в строке
состояния.

Исключение сделано только для Bluetooth. Tuya, WLED и Hue работают через
сеть, и их обслуживает служба — это позволяет подсветке работать, даже
когда окно приложения закрыто.

## Связь приложения и службы

Приложение и служба общаются через **локальный сокет** на петлевом
интерфейсе: `127.0.0.1:51823`. Порт слушает только петлевой адрес, то есть
снаружи он недоступен, а брандмауэр не затрагивается.

Изначально связь шла через именованный канал, и это оказалось неудачным
выбором. Доступ к каналу, созданному службой с высокой целостностью,
ограничивается **обязательным уровнем целостности** вызывающего процесса:
приложение, запущенное обычным пользователем, получало отказ в доступе,
хотя права доступа его разрешали. Внешне это выглядело как «служба не
отвечает» при работающей службе. Снять ограничение можно только меткой в
системном списке доступа, для чего службе нужна привилегия
`SeSecurityPrivilege` — на практике получить её не удалось.

Локальный сокет таких ограничений не имеет: соединение доступно любому
процессу на этой же машине, независимо от уровня целостности.

Соединение открывается на каждую операцию и закрывается сразу после неё.
Постоянное соединение здесь ненадёжно: служба может перезапуститься, а
клиент об этом не узнает и будет считать мёртвое соединение рабочим.

### Если связь не устанавливается

Журнал `service_link.log` рядом с приложением пишет причину каждого сбоя.
Это первое, что стоит посмотреть.

Проверить связь вручную:

```
tools\PipeTest\bin\Release\net10.0-windows\OpenTuyaSync.PipeTest.exe ping
```

## Проверка подсветки: тест цветовой заливки

Отдельная программа заливает весь экран плавно меняющимся градиентом.
Она нужна, чтобы **убедиться, что лампа следует за изображением**, и
посмотреть, насколько плавно устройство принимает смену цвета.

```
tools\ColorTest\bin\Release\net10.0-windows\OpenTuyaSync.ColorTest.exe
```

Возможности:

- **от 2 до 10 цветов** — добавляются и удаляются кнопками, любой цвет
  меняется щелчком по образцу;
- **пять эффектов** — переливание, стробоскоп, по диагонали, из центра,
  вращение;
- **стробоскоп** — экран залит одним цветом; цвет держится заданный
  интервал и **плавно переходит** в следующий. Это не переливание:
  переход идёт один раз между двумя цветами, а не течёт по экрану;
- **скорость смены** — регулятор, показывающий, за сколько секунд
  проходит полный круг по выбранным цветам;
- **интервал удержания** — отдельный регулятор для стробоскопа (0,1–5 с);
- **яркость** — общий множитель, чтобы проверить лампу на слабом свете;
- **полный экран** — `F11` или двойной щелчок, выход по `Esc`;
- **пауза** — `Пробел`;
- панель управления **скрывается сама** через 2,5 секунды без движения
  мыши и возвращается при движении, чтобы не закрывать заливку.

Проверить отрисовку без показа окна:

```
OpenTuyaSync.ColorTest.exe --selftest
```

Режим сохраняет кадр каждого эффекта в PNG, снимает серию кадров
стробоскопа и проверяет по ним, что цвет меняется постепенно. Отчёт
пишется в `selftest_report.txt` рядом с программой: у оконной программы нет
консоли, и без файла результат было бы нечем проверить.

## Иконка приложения

Иконка собирается скриптом [assets/make_icon.py](../assets/make_icon.py) из
готового изображения `assets/icon_source.jpg`: монитор с радужной
подсветкой по краям и знаком Bluetooth на экране.

Изображение не рисуется кодом: в исходнике уже есть объём, стеклянный
отблеск экрана и мягкое цветное свечение, а попытки повторить это
векторами давали заметно более бедный результат. Знак Bluetooth в исходнике
тоже правильный по начертанию.

Что делает скрипт:

- **убирает фон** -- он залит чёрным, поэтому прозрачность берётся из
  яркости исходника: свечение по краям остаётся, фон исчезает;
- **делает монитор непрозрачным** изнутри, включая тёмную рамку: иначе
  полупрозрачные пиксели просвечивают фоном и иконка выглядит выцветшей;
- **обрезает служебную подпись** внизу исходника;
- вписывает изображение в квадрат и уменьшает до нужных размеров.

```bash
python assets/make_icon.py
```

Скрипт создаёт `assets/icon.ico` (размеры 16, 24, 32, 48, 64, 128, 256) и
`assets/icon.png` — крупную версию для документации. Уменьшение идёт из
исходника в 2048 пикселей, поэтому края остаются гладкими.

Иконка **встраивается в исполняемые файлы** через свойство
`ApplicationIcon` в проектах приложения, службы и теста подсветки, а в окне
показывается через `Icon` в разметке. Одного файла рядом с программой
недостаточно: без `ApplicationIcon` Windows берёт системный значок.

Службу для диагностики удобно запускать с выводом в консоль:

```bash
OpenTuyaSync.Service.exe --console
```

## Что проверено, а что нет

Честно, без прикрас.

**Проверено на реальном оборудовании:**

- **Bluetooth-лента ELK-BLEDOB (BE:60:41:00:27:B9) — работает
  полностью.** Найдена сканированием, служба `FFF0` и характеристика
  записи `FFF3` совпали с ожидаемыми, лента меняет цвет (проверены
  зелёный, синий, жёлтый, оранжевый, красный) и включается/выключается.
  Три команды подряд прошли без единой ошибки.
- **Служба подключается к ленте**: в состоянии устройств — «Лента
  ELK-BLEDOB — подключено, BE:60:41:00:27:B9», цвет доходит через канал.
- **DXGI Desktop Duplication работает**: 60 кадров из 60 на адаптере
  NVIDIA GeForce GTX 1060, в том числе при запущенной 3D-игре
  (Borderlands 2, полноэкранный режим).
- **Связь агента со службой**: команда проходит, ответ приходит,
  **кадр цвета — 0,14–0,26 мс** (горячий путь подсветки).
- **Захват экрана даёт живые цвета**: 0,29–0,39% одного ядра, цвета
  меняются вместе с содержимым экрана.
- **Автоматический переход на резервный захват GDI**, когда DXGI
  недоступен.
- **Приложение запускается**: окно открывается и отвечает, память ~85 МБ.
- Конфигурация читается и записывается, формат совместим с Python-версией.

**Не проверено:**

- **Лампы Tuya, WLED и Hue.** Устройств нет; протокол Tuya перенесён из
  проверенной Python-версии байт в байт (кадры, AES-128-ECB,
  HMAC-SHA256, CRC32), но на живой лампе не подтверждён.
- **Сканирование сети** — требует устройств Tuya в локальной сети.
- **Режим музыки** — WASAPI loopback и FFT написаны, на реальном звуке не
  проверялись.
- **Установка службы** — требует прав администратора; код написан и
  компилируется, но реальную установку я не выполнял.
- **Полная цепочка «экран → служба → лента» одним запуском.** Каждое
  звено проверено отдельно и работает, но собрать их вместе в моей среде
  не удалось: интерфейс запускается только интерактивно. Проверьте у себя
  кнопкой «Запустить» на вкладке «Автоматически».

### Ограничения моей среды

Интерфейс приложения я проверить «глазами» не могу: запуск оконных
программ из моей среды ненадёжен, а процесс завершается вместе с
командой. Поэтому для проверки агента я добавил файл-признак работы
`agent_alive.txt` рядом с `.exe` — он обновляется каждые 5 секунд, пока
приложение живо. Это самый быстрый способ убедиться, что оно запустилось.

## Отличия от Python-версии

- **Убраны источники Spotify и веб-камера.** Осталось три: экран, музыка,
  вспышки. Добавить остальные можно по образцу — это один класс и одна
  ветка в `SourceFactory`.
- **Добавлены точечные улучшения**: выбор устройства вывода звука,
  персональная яркость для каждого устройства, области захвата в
  настройках, автозапуск, горячие клавиши, установка службы.
- **Формат config.json совместим**, но пути другие: конфигурация лежит
  рядом с исполняемым файлом.
